rel=nofollow vs rel=nofollow,noopener — Measured in a Real Browser

The usual explanation is about PageRank, which is unobservable. The part that is observable is the HTTP request, and almost every statement about nofollow conflates the two. So I served a page with five links differing only in their rel attribute, clicked each in Chrome, and recorded the Referer the destination received.

14 November 2026, extended 15 November 2026 · Chrome 157 via CDP · up to five local origins, one per site relationship

The claim under test

Common statements about rel="nofollow", in descending order of confidence:

  1. It tells search engines the link is not an endorsement. This is what the spec says.
  2. It does not stop the click from working, or stop the visit from being counted by the destination. Testable.
  3. It does not change what the browser sends in the request. Testable, and I had never seen it tested.
  4. It prevents the link from passing PageRank. Not observable from outside Google.

Point 4 is the one everybody argues about and nobody can measure. Points 2 and 3 are measurable in a few minutes, and they determine whether a nofollow link is worth placing for traffic reasons — a separate question from its ranking effect.

Experiment 1 — five rel variants, same target

Two http.server instances on 127.0.0.1:8765 and :8766. Because the port differs, the browser treats them as different origins, which is what exercises the cross-origin referrer rules. The page on 8765 contains ten links: five rel variants pointing at 8765, and the same five pointing at 8766. Every link is otherwise byte-identical.

LINKS = [
    ("plain",         ""),
    ("nofollow",      ' rel="nofollow"'),
    ("nofollow_ugc",  ' rel="nofollow ugc"'),
    ("noreferrer",    ' rel="noreferrer"'),
    ("noopener",      ' rel="noopener"'),
]

Each link was clicked programmatically through the DevTools Protocol, and the destination logged self.headers.get("Referer"). Results, for a click from http://127.0.0.1:8765/ to http://127.0.0.1:8766/target:

rel on the linkReferer received by destination Header present
(none)http://127.0.0.1:8765/yes

nofollow ugchttp://127.0.0.1:8765/yes
noreferrerabsentno
noopenerhttp://127.0.0.1:8765/yes

Same-origin results were identical except that the full path was included (/target?k=plain etc.), which is the expected path-level difference between same-origin and cross-origin defaults.

The finding is unambiguous: rel="nofollow" does not alter the request in any way. The destination receives exactly the same Referer, and the same Sec-Fetch-Site: same-site, as a plain link. If a site owner reads their referrer log, a nofollow visit is indistinguishable from a followed one. Only noreferrer strips it — and noreferrer also implies noopener, which is a different feature entirely.

So "nofollow links still pass traffic" is correct, and for a duller reason than people assume. The browser never knew or cared about the rel value when building the request. The click is a navigation like any other. The rel attribute is metadata consumed after the fact, by crawlers, not a transport modifier.

Experiment 2 — what actually removes the referrer

If rel does not govern this, Referrer-Policy does. Same setup, except the source page is served with a different Referrer-Policy response header per run, on 8775 → 8776:

Referrer-Policy on sourceReferer received cross-origin
no-referrerabsent
originhttp://127.0.0.1:8775/
origin-when-cross-originhttp://127.0.0.1:8775/
strict-origin-when-cross-originhttp://127.0.0.1:8775/
unsafe-urlhttp://127.0.0.1:8775/?pol=unsafe-url

This is the matrix that matters operationally. A site that wants referrer credit for outbound links gets it under the browser default (strict-origin-when-cross-origin, which strips the path but keeps the host), and loses it entirely under no-referrer. Note the unsafe-url row: the path survives cross-origin only under that policy, which is why full referrer paths are so rare in analytics.

Checking the two domains in this cluster directly with curl -I:

HostReferrer-Policy sentEffect on outbound clicks
celticgemini001.github.ionot set (browser default) host sent, path stripped
upgolab.comno-referrer nothing sent at all

That second row is worth sitting with. A site that sends Referrer-Policy: no-referrer is invisible in the referrer logs of everything it links to. If you are judging a link-building effort by destination-side referrer reports, links from such a site will look like direct traffic. The visits are real; the attribution is gone. Any measurement of off-site linking that relies on destination referrers is therefore blind to every source site configured this way — which is a meaningful and growing share of the web.

Experiment 3 — the comma that silently disables the attribute

The first two experiments treat rel as a single token. It is not. It is a set of tokens, and the HTML standard says they are separated by ASCII whitespace — U+0009, U+000A, U+000C, U+000D, U+0020. A comma is not in that list. So rel="noopener,noreferrer" — the form that looks correct to anyone coming from a CSS selector list or a comma-separated header — parses as one token spelled noopener,noreferrer, which matches neither keyword.

This is not a style question. In the SEO world a mis-parsed nofollow is the difference between a link you asked Google to ignore and a link you did not. I had never seen the failure measured, so I put eight rel values in one page and read relList back from a live DOM:

rel as writtenParsed tokens nofollow present
nofollow["nofollow"]yes
nofollow,noopener["nofollow,noopener"] no
nofollow, noopener["nofollow,", "noopener"] no
nofollow,ugc["nofollow,ugc"] no
sponsored,nofollow["sponsored,nofollow"] no
nofollow ugc["nofollow", "ugc"]yes
nofollow noopener noreferrer ["nofollow", "noopener", "noreferrer"]yes

Every comma row fails, and the comma-plus-space row fails for a subtly worse reason: the trailing comma becomes part of the first token, so "nofollow," is not "nofollow". A link written rel="nofollow, noopener" is therefore followed by every consumer that splits on whitespace, which is what the standard mandates. The author's intent and the machine's reading diverge, and nothing warns you.

This is the highest-cost mistake in the table, and it fails silently. A link meant to be nofollow ships as dofollow. In affiliate or sponsored-content contexts that is exactly the case search guidelines care about, and the markup looks correct to human review. The fix is one character: replace the comma with a space.

Experiment 4 — does the comma also break noreferrer at the network layer?

Parsing is not enforcement, so the token check above only proves the DOM disagrees with the author. The question that matters is whether the browser still honours the intent. Same two origins, enforce.html on :8790 linking to :8791, but now the destination logs the document request — Sec-Fetch-Dest: document — and records self.headers.get("Referer") plus what page JavaScript sees:

noopener+TAB+noreferrerabsent emptystripped

noopener+U+00A0+noreferrer http://127.0.0.1:8790/http://127.0.0.1:8790/ leaks — NBSP is not ASCII whitespace

The comma row was run three times, in two separate browser sessions, and leaked every time; this is deterministic parser behaviour, not a race. The NBSP row is the same bug wearing a different disguise: a non-breaking space looks like a separator in an editor and is not one, so the whole string collapses into a single unrecognised token. And the upper-case row is worth noting precisely because relList reports ["NOOPENER", "NOREFERRER"] — the tokens are preserved verbatim — while the browser still strips the referrer. Token matching is case-insensitive; the list is not normalised.

Experiment 5 — the window.opener trap that is not about rel

The noopener half needs its own control, because modern Chrome applies noopener implicitly to target="_blank". That default makes any naive test useless: every _blank link shows a severed opener whether or not rel contributed. Measured with window.open() instead, where the implicit default does not apply:

window.open(url, '_blank')                  // opener survives
window.open(url, '_blank', 'noopener=yes')  // opener severed
Navigationwindow.opener alive Destination can read opener
window.open(url, '_blank')1 yes — location readable
window.open(url, '_blank', 'noopener=yes') 0no
<a target="_blank">, no rel0 no — browser implies noopener

So the first table's opener=0 column carries no information about rel: Chrome 157 severs the opener for any _blank anchor by default. The only place noopener still does work by hand is window.open() and legacy or embedded browsers. If you are auditing rel values by checking window.opener on a _blank link, you are measuring the browser default and will conclude every link is safe.

Experiment 6 — the tri-state the Referer header cannot tell you

Every table so far recorded one bit per click: the header arrived, or it did not. That bit is not what an attribution system needs. A destination asking "where did this visit come from" wants a host, a path, and a relationship — and it turns out the browser answers those three questions with two different mechanisms, one of which ignores Referrer-Policy entirely.

Three relationships, built from loopback addresses rather than DNS, because the definition of "site" here is the registrable domain and loopback lets me control it exactly:

  • same-origin — 127.0.0.1:8840 → 127.0.0.1:8840. Scheme, host and port all match.
  • same-site — 127.0.0.1:8841 → 127.0.0.1:8842. Different origin, same site: the port is not part of a registrable domain.
  • cross-site — localhost:8843 → 127.0.0.1:8844. localhost and 127.0.0.1 are different hosts, therefore different sites, even though they route to the same machine.

Seven Referrer-Policy values, set as response headers on the source document, crossed with the three relationships: 21 real navigations, each a mouse click dispatched through the DevTools Protocol, each destination logging the headers it actually received.

Referrer-Policy on sourcesame-origin same-sitecross-site
(no header — default)full URL + query origin onlyorigin only
no-referrer absent in all three
originorigin onlyorigin onlyorigin only
origin-when-cross-originfull URL + query origin onlyorigin only
strict-origin-when-cross-originfull URL + query origin onlyorigin only
unsafe-urlfull URL + queryfull URL + query full URL + query

The default is not "the referrer is sent". It is "the referrer is sent as an origin to anyone who is not byte-identical to you". A destination reading its referrer log under the browser default therefore recovers the host of the linking page and nothing else — no path, no query string.

Count the cells by what a destination can actually recover, rather than by raw header string: 21 cells collapse to three shapes — nothing, origin, or full path with query. The 21 log lines contain 11 distinct raw values only because every cell was loaded from a different source path, which is noise in this measurement, not signal. Five cells are the empty set.

Two rows are worth more than a glance. origin-when-cross-origin and strict-origin-when-cross-origin produced the same shape in all three columns — full, origin, origin — zero divergence across nine cells. Their raw header strings differ only in the source path, which is expected: each policy was served from its own URL. The strict prefix changes behaviour in exactly one case, and my matrix does not exercise it: an HTTPS source linking to a plaintext HTTP destination, where it withholds the header instead of downgrading it. For any pair of documents on the same scheme the two policies are the same policy, so swapping one for the other is not a privacy improvement and does not change what analytics sees. The honest limit of this section is that the scheme-downgrade case is asserted from the spec, not measured here.

The same-origin row is the one that surprises people. It reads as "only send the referrer when the destination is me", and it does that, but it classifies 127.0.0.1:8841 → 127.0.0.1:8842 as not me and drops the header entirely. Origin and site are different partitions, and only the two policies with "cross-origin" in the name respect the wider one.

The second signal, which Referrer-Policy does not touch

All 21 requests also carried Sec-Fetch-Site, and it was populated in 21 of 21 — including the five requests that carried no Referer at all. So a destination that receives nothing still learns something precise:

What the destination receivedCountStill knowable
Referer header present16 / 21 host, plus path if same-origin
Sec-Fetch-Site present21 / 21 same-origin / same-site / cross-site, always
Navigation context (Sec-Fetch-Mode: navigate, Sec-Fetch-User: ?1, Sec-Fetch-Dest: document) 21 / 21it was a click, not a subresource fetch

That is the correction to the tidy story in the previous section. Setting no-referrer does not make a site invisible to the destinations it links to. Those destinations still see a cross-site, user-initiated document navigation and can log it as such. What they lose is the identity of the source — which is exactly the part an attribution report needs, and exactly the part a parameter survives.

Applying it to this cluster, honestly

This is not a hypothetical. The thirteen pages in this cluster are served from celticgemini001.github.io, which sends no Referrer-Policy header — checked with curl -I, not assumed — so the browser default applies. Every link from these pages to the product site is cross-site. By the table above, the product site's referrer log receives https://celticgemini001.github.io/ and never the path.

So I counted the links. Thirteen pages, all outbound links to the product host, and how many carry any attribution parameter — measured before and after the two links on this page were fixed:

Two of twenty-four is not a fix, it is a demonstration. The other twelve pages still resolve to one referrer row, and the honest reading of that column is that this cluster is not yet measurable, not that it is measured.

Twenty-two of the twenty-four links still resolve to one referrer row. If any of them converts, the report will say "celticgemini001.github.io" and stop there. And it is worse in the other direction: the product site itself sends Referrer-Policy: no-referrer, so its own outbound clicks are not attributed in anyone's log — real visits that will be filed as direct traffic everywhere they land.

The fix costs one query string. The two links at the foot of this page now carry utm_source and utm_medium, because the measurement above says the header cannot do that job and pretending otherwise is how a link-building effort ends up with no data after three months of work.

# which of your links can a referrer-based report actually distinguish?
python3 - <<'PY'
import glob, re
hits = utm = 0
for f in glob.glob('**/index.html', recursive=True):
    h = open(f, encoding='utf-8').read()
    for href in re.findall(r'<a\s[^>]*href="([^"]+)"', h):
        if 'upgolab.com' in href:
            hits += 1
            utm += 'utm_' in href
print(f'{hits} outbound links, {utm} distinguishable')
PY

And to confirm the policy half without a browser, one header read per host:

for h in celticgemini001.github.io upgolab.com; do
  printf '%-28s ' "$h"; curl -sSI "https://$h/" | grep -i '^referrer-policy' || echo '(none — browser default)'
done

Checking a real site in ten seconds

None of this needs a browser. The parser rule is simple enough to apply to your own HTML in one grep, and it catches both failure modes at once — the comma and the lookalike space:

# anchor-scoped: a comma inside a real link's rel
grep -rEo '<a [^>]*rel="[^"]*,[^"]*"' --include='*.html' .

# non-ASCII whitespace inside rel (NBSP, thin space, etc.)
grep -rPo '<a [^>]*rel="[^"]*[\x{00A0}\x{2000}-\x{200B}][^"]*"' --include='*.html' .

The <a anchor in both patterns is not decoration. Scoping the match to an opening tag is what keeps the check honest — an unscoped version of the first pattern also matches this very paragraph's prose, and any page that documents the bug will trip its own linter. That is the difference between a check you can wire into a deploy and one you disable after the second false positive.

Run against this cluster of thirteen pages: zero comma matches and zero non-ASCII-space matches. The 24 outbound links to the product site carry no rel at all, and the twelve internal navigation links on each page are plain <a href> — deliberate, since the whole point of the cluster is a crawlable path rather than a protected one. The value of a check like this is that it is cheap enough to run on every deploy, and it fails on the exact class of mistake that review does not catch.

What this changes about placing links

  • Judge nofollow links by traffic, not by "link juice". The traffic is fully real, and it is measurable at the destination. The ranking effect is not measurable by you, which means it should not drive the decision.
  • If you need attribution, you need a parameter. Because the browser may strip the referrer and the source site may strip it too, a ?utm_source=-style parameter is the only attribution that survives every policy in the matrix above.
  • A nofollow link on a page with no-referrer is doubly invisible to a referrer-based audit, and identical in effect to a followed link on a page without it. The two attributes are orthogonal, and conflating them is the source of most of the bad advice on this topic.

Reproducing it

# two origins: different port = different origin for referrer purposes
python3 - <<'PY'
import http.server, threading, json
class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        print(json.dumps({"port": self.server.server_address[1],
                          "path": self.path,
                          "referer": self.headers.get("Referer")}))
        body = b'<a id=t href="http://127.0.0.1:8766/target" rel=nofollow>go</a>'
        self.send_response(200); self.send_header("Content-Length", str(len(body)))
        self.end_headers(); self.wfile.write(body)
for p in (8765, 8766):
    threading.Thread(target=http.server.ThreadingHTTPServer(("127.0.0.1", p), H)
                     .serve_forever, daemon=True).start()
threading.Event().wait()
PY

# then click it in a real browser and read the referer the second server printed

The measurement is four lines of server and one click. It is worth running once, because the result is counter-intuitive in a way that reading the spec does not fix: the rel attribute simply is not consulted when the request is built.
